Isolation Anomalies in Spring @Transactional Code on PostgreSQL

A strategy × isolation-level study with a dependency-cycle checker

Skewer experiment report · run 20261010-112454 · 10 Oct 2026

Abstract

Spring's @Transactional makes a method atomic but leaves its isolation to the database, which for PostgreSQL defaults to Read Committed. We implement one banking service six ways and run each implementation at three isolation levels under 32 concurrent clients on 20 accounts, 5 seeds per configuration. Every committed transaction's reads and writes are recorded with exact row versions, and a checker searches the resulting direct serialization graph for cycles, classified with Adya's taxonomy. The textbook load-modify-save implementation at the default level violated an invariant in 5 of 5 runs, creating a median of €5,603.00 per run. Across all 23 configurations, 9 produced at least one anomaly. 23 of 23 predictions made before the experiment were confirmed. The checker reported no anomaly in 30 of 30 negative-control runs and detected the known defect in 20 of 20 positive-control runs. We report the throughput, latency and abort cost of every configuration that preserved the invariants.

1Introduction

Concurrency defects in money-moving code pass unit tests and surface in production as balances that do not add up. A common belief among Spring developers is that annotating a method with @Transactional makes it safe. The annotation guarantees atomicity; isolation, the question of what concurrent transactions may observe of each other, is delegated to the database. PostgreSQL implements Read Committed, Repeatable Read (snapshot isolation) and Serializable (serializable snapshot isolation) [1, 7].

This report asks which common implementation strategies preserve two business invariants under each level, and at what cost. Rather than infer correctness from final balances alone, every execution is checked for dependency cycles that no serial execution could produce, following the method of Elle [3] and the anomaly definitions of Adya et al. [4].

2Method

2.1System under test

A Spring Boot service exposes four operations: transfer, withdraw (an account may not fall below zero), joint withdraw (a customer's two joint accounts may not sum below zero, though each may) and a read-only total balance. Each is implemented by six strategies, every one executed inside a proxy-managed @Transactional boundary at the requested isolation level:

naive-jpa
Load the entity, compute the new balance in Java, let dirty checking write it.
atomic-update
Push the check into one statement: UPDATE … SET balance = balance − :amt WHERE id = :id AND balance ≥ :amt.
pessimistic
SELECT … FOR UPDATE on every account involved, in account-id order, before reading balances.
pessimistic-unordered
The same locks, taken in request order.
optimistic
JPA @Version on the account, with a retry wrapped around the whole transaction.
serializable-retry
The naive-jpa code unchanged, at Serializable, retried as a whole on SQLSTATE 40001.

Two further configurations reproduce known Spring pitfalls: a @Transactional(isolation = SERIALIZABLE) method reached by self-invocation, and a retry loop placed inside the transactional method.

2.2Instrumentation

Each account row carries last_writer, the identifier of the transaction that wrote that version. Every read returns it, so each transaction's read set names exact versions. An AFTER UPDATE trigger records, for every committed write, the version it replaced, taken from the row PostgreSQL actually overwrote. A txn_log row inserted as the transaction's final statement exists if and only if the transaction committed, and records the isolation level that actually ran (SHOW transaction_isolation) and the database transaction identifier. Identical instrumentation is applied to every strategy; throughput is additionally measured with it disabled.

2.3Checker

The checker operates offline on saved histories in two layers. The first evaluates business invariants: atomicity, conservation of money, exactly-once application of effects, the account and customer rules, and read consistency of reports. The second builds the direct serialization graph with write-write (ww), write-read (wr) and read-write anti-dependency (rw) edges. Because the version order is observed rather than inferred, serializability checking reduces to cycle detection. Strongly connected components are found with Tarjan's algorithm; the shortest cycle through each anti-dependency is found by breadth-first search and classified as G0, G1c, G-single or G2-item [4]. Cycles are further labelled as lost update, read skew or write skew [5, 6].

3.6Validity of the checker

A checker that reports false anomalies would invalidate every result above, so no result was accepted before the following passed. Offline, the checker classified hand-built histories for each anomaly class exactly, reported nothing for 10,000 randomly generated serial histories, flagged every history in which one read-modify-write was mutated to read a stale version, and agreed with JGraphT's strongly connected components on random graphs. End to end, the negative control (every strategy at Serializable) produced 0 reports in 30 runs, and the positive control (the naive strategy at Read Committed) was detected in 20 of 20 runs, with the first complete counterexample after a median of 0.05 s (negative: 2 s / 1,000 ops per run; positive: think time 0-20 ms, 10 s per run).

5Threats to validity

Throughput and latency were measured on a single laptop with PostgreSQL in Docker Desktop, at deliberately high contention; they support comparisons between strategies, not absolute capacity claims. The workload uses item reads only, so predicate anomalies and phantoms are outside the scope of the checker. The instrumentation adds writes to every transaction; the uninstrumented baseline in Table 4 bounds its effect. A run in which no anomaly is found is evidence, not proof, that a configuration is correct. Seeds fix operation streams but not thread interleavings, so individual runs are not repeatable bit for bit; every failing history was saved and can be re-analysed offline.
